## 1. What Orca is, in one paragraph

Orca is an MIT-licensed Electron app (Electron 43, React 19) with ~137k stars that ships about 1.6 releases a day. It started in March 2026 as a "worktree + terminal manager for CLI agents" and has since grown into an agent platform:
- **Agents:** it runs ~40 agent CLIs as raw terminals or in a native Chat UI (Claude Agent SDK, `codex app-server`, ACP).
- **Coordination:** coordinator/worker orchestration, scheduled and event-triggered automations, and persistent **Bots**. Bots have `SOUL.md` and `MEMORY.md`, take requests from Slack, Linear and GitHub through an outbound-only cloud relay, and delegate code work to workers in child worktrees.
- **Hosts:** a headless `orca serve` runtime, a managed server auto-deployed to SSH hosts, WSL-as-host, and an E2EE mobile companion with push.
- **Built-in tools:** a Chromium browser with Design Mode, computer use on all three OSes, an iOS/Android emulator bridge, and on-device dictation.
- **Agent-facing surface:** a self-describing `orca` CLI that agents use to drive everything, and a plugin system with a catalog.

Its chronic weakness is performance and memory, which is structural to Electron. Its top-voted gaps are:
- multi-repo workspaces (#1099, 123 reactions)
- multiple windows (#6074, 77)
- a real editor with LSP (about 183 reactions across four issues)
- Jujutsu (#1082, 60)
- account pinning and failover

## 2. Architecture summary

Details and source paths are in the Architecture sections of Parts A–D.

1. **Processes.** Orca runs an Electron main process and a React renderer. Separate HTML roots serve the app, a pop-out dashboard, "Space" and a browser web client. Alongside them:
   - a utility-process **backend** (`src/main/backend`) linked over a MessagePort;
   - a long-lived **terminal daemon** (`src/main/daemon`);
   - **orcad** (`src/main/orcad`), the plain-Node runtime that `orca serve`, SSH hosts and WSL distros also run;
   - about 37 single-purpose workers: session-search, usage-scan, bots-db, journal-sql, profile-state writer, parcel watcher, STT, computer-use sidecar, plugin host, and others.
2. **The terminal daemon outlives the app.** It owns every node-pty session and survives quit, crash and app update. It speaks NDJSON control plus a binary-framed stream over a private Unix socket or Windows named pipe, with a hello-token handshake. Its protocol is version-gated (`PROTOCOL_VERSION = 62`) so old daemons stay attachable.
   - A link/probe/rename protocol prevents a new daemon from deleting a live daemon's socket.
   - A headless xterm in the daemon writes `checkpoint.json`, `output.log` (≤5 MiB), `meta.json` and `scrollback.bin` per session, mode 0600.
   - Known pain: old daemon generations leak after updates (#9138).
3. **Storage.** Profile state moved from `orca-data.json` to SQLite `profile-state.db` in v1.4.214, using built-in `node:sqlite` with a writer worker, atomic snapshots and backups.
   - Other SQLite stores: `orchestration.db`, a per-host bot items DB, and a session-search index.
   - Keybindings live in `~/.orca/keybindings.json` and bots in `~/.orca/bots/<folder>/`.
   - Managed agent homes: `claude-profiles/<id>/home` and `codex-accounts/<id>/home`.
   - Foreign readers parse other agents' session databases, for example OpenCode's.
4. **RPC.** The core is `src/main/runtime/orca-runtime.ts`, with 116 RPC method modules and Zod contracts in `src/shared/rpc-contract`. Three transports carry it:
   - a Unix socket or named pipe for the local CLI, authenticated by an `authToken` in `orca-runtime.json`;
   - a WebSocket on port **6768** for paired clients, with an E2EE handshake (X25519 + NaCl secretbox, v2 key schedule, per-direction keys, transcript hash) and revocable device tokens;
   - the cloud relay.
   About 80 Electron IPC domains sit on top for the renderer.
5. **Agent status uses two channels.**
   - **Hooks first.** Orca installs managed hooks into each agent's config. For Claude these cover SessionStart, UserPromptSubmit, Stop, StopFailure, Subagent*, Pre/PostToolUse, PermissionRequest, PostCompact, Elicitation and SessionEnd. Each hook `curl`s `http://127.0.0.1:$ORCA_AGENT_HOOK_PORT/hook/<agent>` with a token and pane identifiers, with a 0.5 s connect and 1.5 s max timeout. Hooks re-source `{userData}/agent-hooks/endpoint.env` on every call, so agents that outlive an app restart still reach the new server. On Windows a native Rust hook replaces `.cmd` + curl.
   - **OSC 7501 second.** This is the "Program Status Protocol" (Claude ≥2.1.295, Codex, Grok, pi, omp, Kimi). Agents write it into the PTY stream after Orca answers a probe. It is used when hooks have been silent for 2 minutes.
   - **Terminal titles last.**
   - **States.** Ranked from most to least urgent: waiting, blocked, permission, failed, unconfirmed, working, monitoring, interrupted, unverifiable, done, idle. The **unverifiable** state means a PTY is alive but its reporting is stale.
6. **Native chat engines.** Claude runs through `@anthropic-ai/claude-agent-sdk` (stream-json) and Codex through `codex app-server` JSON-RPC. About 20 others go through ACP dialects (`src/main/acp`); binaries can be fetched from the official ACP registry. The rest use transcript readers.
7. **Orchestration.** Runs, tasks, dispatches, messages and gates live in `orchestration.db`.
   - Mail is never typed into an agent. An idle terminal agent gets a one-line pointer ("You have N orchestration messages. Run `orca orchestration check --run <id>`"). Native chats get a queued structured turn.
   - Defaults: 4 concurrent workers, a circuit breaker after 3 failed dispatches, nesting up to 4 levels.
   - Workers get a dispatch preamble (task ID, dispatch ID, coordinator address, CLI contract, optional BASE DRIFT, spec) and must send `worker_done` exactly once.
8. **CLI.** Every `orca` command is a declarative `CommandSpec` (`src/cli/specs`). Help, typo suggestions and `orca agent-context` (a machine-readable schema for agents) are generated from those specs. Remote servers are selected with `--environment`.
9. **Automations** run on a 60 s tick in main or `orca serve`. Schedules use 5-field cron, presets or a restricted RRULE with a timezone and missed-run grace. Event triggers arrive from Orca Cloud connector webhooks.
10. **Bots.** A bot is a profile record plus a folder: `AGENTS.md`, `CLAUDE.md`, `bot.json`, the user-owned `SOUL.md` and `MEMORY.md`, plus `memory/` and `skills/`.
    - It runs as a native-chat session of the user's own agent CLI, and controls Orca by shelling out to the `orca` CLI.
    - It delegates code work to workers in `--worktree new-child`.
    - Guards enforced in code: a read-only allow-list for "look around", a tool-less memory tidy-up, and secrets kept out of the agent via a loopback MCP credential relay where Orca is the OAuth 2.1 client.
11. **Cloud.** The desktop never opens a port. Four services carry its traffic:
    - **Connector service** (closed source). The desktop long-polls `/v1/connector/poll` with a 50 s hold, ≤20 deliveries or 8 MB per poll, and a 30 s lease. A person's request waits up to 24 h for a sleeping machine.
    - **Wake channel.** A Cloudflare Durable Object holds a WebSocket per host that only ever sends `{"type":"wake"}`, with a 25 s keepalive.
    - **Mobile relay.** A director (`relay.onorca.dev`) assigns regional cells that splice E2EE frames between phone and desktop.
    - **Push gateway** (APNs/FCM). The desktop gets a 24 h session by answering an X25519 challenge. The gateway logs only counters.
12. **SSH.** Orca supports both ssh2 and system OpenSSH (ControlMaster, Kerberos, MFA, host-key verification). On first connect it **uploads Node and orcad to the host**, compiling node-pty there on Linux, so remote PTYs are leased by the host and survive the laptop closing.
13. **Mobile.** The app is Expo 58 / React Native 0.88. The desktop serves the phone's web UI bundle over the paired link, verified against manifest hashes, so UI ships without app-store releases.
14. **Native code.**
    - Swift computer-use helper on macOS; PowerShell UI Automation on Windows; Python AT-SPI on Linux.
    - Rust Windows hook and `orca.exe` launcher (the script version kept getting deleted by antivirus).
    - C provider-exec subreaper, journal lock and Wayland clipboard.
    - C++ addons for the Windows registry, notifications and security.
15. **Speech** runs on-device with sherpa-onnx models (Parakeet, SenseVoice, Zipformer, Nemotron) via transcribe-cpp/koffi in an STT worker. An OpenAI-compatible cloud backend is optional.
16. **Plugins.** The manifest is `orca-plugin.json` v2, with four execution profiles: data, declarative, sandboxed-ui (a per-plugin webview with networking cut) and trusted-worker (unsandboxed Node that can veto or rewrite launches and tool calls).
    - Catalog entries are pinned to a commit SHA and a sha256 hash.
    - Releases wait 12 h before auto-install, and the kill list refreshes every 6 h.
    - An Orca Cloud team policy can require or block plugins.
17. **Performance is a structural fight.** The repo keeps "only-shrink" ratchets of known main-thread blocking calls; one helper list alone has 1,577 entries. A fleet perf gate (1,900 workspaces, 1,800 chats, 200 terminals; 25–35 min per run, not in CI) guards releases. The retired terminal perf suite failed its last run: 104 ms median typing latency against a 75 ms budget at 50 PTYs.

## 3. Where Orbit beats Orca (strategy)

- **Native performance as the headline.** Orca's own maintainers run a "Performance 100x'd" thread (#43246), and users report:
  - 20+ GB GPU leaks from xterm WebGL atlases (#38108);
  - a Linux OOM after about 44 h (#19831);
  - Windows freezes with about 5 terminals (#11363);
  - a 50% GPU load while idle on macOS (#9576).

  Orbit should publish its own budgets and meet them: a GPU-rendered terminal with a capped glyph atlas, near-0% CPU and GPU at idle, and typing latency under 16 ms at 50 PTYs.
- **Take the top-voted gaps.** Ship multi-root workspaces with a cross-repo diff, multiple windows (trivial in GPUI), a built-in LSP-backed editor and review (Zed-style), a VCS abstraction that can host jj, and account pinning with rate-limit failover.
- **Copy the engine ideas that are right.** Specifically:
  - a PTY daemon that outlives the app;
  - hook-first status with an honest **unverifiable** state;
  - a mailbox-and-pointer orchestration that never types mail into a TUI;
  - an outbound-only connector relay;
  - E2EE pairing;
  - a self-describing CLI generated from command specs;
  - agent account isolation through separate `CLAUDE_CONFIG_DIR` and `CODEX_HOME` folders.

  Write these in Rust as one `orbitd` binary that serves the desktop, headless and SSH roles. Orca needs Node, orcad, the daemon and about 37 workers for the same job.
- **Avoid Orca's breadth trap.** It supports ~40 agents with per-agent modules, while users ask for **user-defined agent manifests** (#2284, #14323). Orbit should support a short list of agents deeply (Claude, Codex, OpenCode, Gemini, Pi) and let users add any other agent through a TOML manifest.
- **Stability over velocity.** At 1.6 releases a day, Orca regularly ships regressions (#6795 "suddenly VERY slow", 55 comments). Orbit should run a weekly stable channel and a nightly.

## 4. Engine work vs UI work

The full per-area split is in the generated index in section 5. These are the clusters that matter for planning.

2. The agent hook server and endpoint file, the OSC 7501 parser, and the status state machine.
3. Account isolation homes and usage polling for Claude OAuth usage, Codex `account/rateLimits/read` and the statusLine feed.
4. The orchestration DB, dispatch preamble, mailbox and wake pointer, and circuit breaker.
5. The automations scheduler: cron, RRULE and missed-run grace.
6. The `orca`-style CLI over a local socket with spec-generated help and `agent-context`.
7. SSH runtime deploy, port forwarding and WSL-as-host.
8. The E2EE pairing protocol, relay, and push.
9. Bot runtime: folder layout, preamble assembly, memory guard and tidy-up, the items DB, and the connector poll/outbox protocol.

11. Skills distribution: stubs, the in-binary guides, and a safe updater.

#### Architecture notes

- **Process model:** Electron main + React renderer, plus a separate long-lived **terminal daemon** (`src/main/daemon`) that owns every PTY, plus **orcad** (`src/main/orcad`), a plain-Node server build of the Orca runtime used by `orca serve`, on SSH hosts, and in WSL. Heavy work (usage scans, port scans, agent identity, spawns on Windows) runs in worker threads / utility workers.
- **Daemon survives app quit/crash/update:** clients talk to it over a private Unix socket (`<userData runtime dir>/…`, or `/tmp/.orca-daemon-<uid>/<sha12>` when the path is too long) or Windows named pipe, NDJSON control + binary-framed stream, with a hello-token handshake. Wire protocol is version-gated (`PROTOCOL_VERSION = 62`) so old daemons stay attachable after app updates. Socket ownership uses a link/probe/rename protocol so a new daemon never deletes a live one's endpoint.
- **Scrollback persistence:** the daemon runs a headless xterm emulator per session and writes `checkpoint.json`, `output.log` (≤5 MiB), `meta.json`, `scrollback.bin` per session dir (encodeURIComponent(sessionId)), mode 0600. Cold restore replays the checkpoint through an emulator, then re-sends terminal modes (alt screen, cursor, etc.).
- **App state storage:** legacy `orca-data.json` migrated to SQLite `profile-state.db` (documents + backups + recovery); keybindings in `~/.orca/keybindings.json`; Claude/Codex managed account homes under userData (`claude-profiles/<id>/home`, `codex-accounts/<id>/home`).
- **Agent status = hooks first, OSC 7501 second, titles third.** Orca installs managed hooks into each agent's config (Claude `settings.json` events SessionStart/UserPromptSubmit/Stop/StopFailure/Subagent*/PreToolUse/PostToolUse/PermissionRequest/PostCompact/SessionEnd/Elicitation…). Hook scripts `curl` POST to `http://127.0.0.1:$ORCA_AGENT_HOOK_PORT/hook/<agent>` with `X-Orca-Agent-Hook-Token` and pane metadata (`ORCA_PANE_KEY`, `ORCA_TAB_ID`, `ORCA_WORKTREE_ID`, `ORCA_AGENT_LAUNCH_TOKEN`), 0.5 s connect / 1.5 s max timeout.
- **Hook endpoint survives restarts:** port/token are written to `{userData}/agent-hooks/endpoint.env` (`endpoint.cmd` on Windows) and re-sourced on every hook call, so PTYs outliving the app reach the new server.
- **OSC 7501 "Program Status Protocol":** agents (Claude ≥2.1.295, Codex, Grok, pi, omp, Kimi) write state into the PTY stream after Orca answers an `OSC 7501 ; ?` probe; used as fallback when hooks are silent 2 min, and as a facet (progress/message) that never decides state.
- **Claude PreToolUse can be blocked by Orca plugins:** POSIX hook waits ≤8 s for an `X-Orca-Hook-Decision: claude-pre-tool-use-v1` answer (Orca answers in ≤6 s); timeout = `{}` (proceed).
- **IPC/RPC:** renderer↔main via Electron IPC/preload; CLI↔runtime via Unix-socket RPC; remote clients↔runtime via WebSocket on default port **6768** with an E2EE handshake (X25519 + NaCl secretbox, v2 key schedule with per-direction keys and transcript hash) and per-client revocable device tokens.
- **Pairing format:** `orca://pair?code=<base64url(JSON)>` with `{v:2, endpoint, deviceToken, publicKeyB64 (Curve25519), scope: mobile|runtime, relay?, hostDescriptor?}`; relay offers carry `directorUrl`, `cellUrl`, `relayHostId`, `inviteToken`, `inviteExpiresAt` (≤10 min).
- **Mobile relay (`cloud/apps/relay`):** phone and desktop each open outbound WSS to a regional relay **cell** (`*.relay.onorca.dev`) assigned by a **director** (`relay.onorca.dev`); the cell splices frames; payloads stay E2EE. Same image runs as director or cell (`ORCA_RELAY_ROLE`); Postgres in prod.
- **Push (`cloud/apps/push`):** desktop authenticates to the push gateway with its X25519 relay key (encrypted challenge → 24 h session), registers phone APNs/FCM tokens, and asks the gateway to push; gateway logs only counters.
- **SSH model:** on first connect Orca uploads Node + orcad to the host (node-pty compiled on Linux, prebuilt on macOS/Windows) and runs the Orca runtime there; SSH PTYs are leased by the remote runtime so they survive laptop app close. Legacy `relay.js --detached` sessions are bridged until they exit.
- **Mobile app:** Expo 58 / React Native 0.88 with WebView; the desktop serves a mobile web UI bundle over the paired connection, verified against manifest hashes (desktop is in the phone's trust boundary).
- **Structured chat engines:** Claude via `@anthropic-ai/claude-agent-sdk` (stream-json), Codex via `codex app-server` JSON-RPC, ~20 others via ACP (Agent Client Protocol) dialects; ACP binaries can be fetched from the official ACP registry (`cdn.agentclientprotocol.com/registry/v1/latest/registry.json`).

## Part B: Review, editing, browser, CLI, orchestration, automations, computer use, emulator, skills

Source: github.com/stablyai/orca, shallow clone at HEAD b864ea6 (2026-11-24). Paths are relative to the repo root. Docs are under `docs/site/content/docs/`.

#### Architecture notes

- **CLI to app transport.** The `orca` CLI (`orca-ide` on Linux) reads `orca-runtime.json` from the Orca userData directory. The file holds the transport endpoints (a Unix socket or Windows named pipe) and an `authToken`. The CLI sends newline-delimited JSON-RPC (`{id, authToken, method, params, orchestration envelope…}`) and ignores keepalive frames. It refuses to connect if the socket directory is not private to the user. The default timeout is 60 s. Source: `src/cli/runtime/connection/transport.ts`, `src/cli/runtime/profile/metadata.ts`.
- **Remote runtimes.** Paired Orca servers (`orca serve`, default port 6768) are reached over a WebSocket transport with capability negotiation. Pairing uses `orca://pair?code=…` and keypair/device tokens (`orca-devices.json`, `orca-e2ee-keypair.json`). `--environment` or `ORCA_ENVIRONMENT` selects the server, and commands carry capability gates for older servers. Source: `src/cli/runtime/connection/websocket-transport.ts`.
- **Command catalog.** Every command is a declarative `CommandSpec` (path, usage, allowedFlags, notes, examples) in `src/cli/specs/*.ts`. Help, typo suggestions and `orca agent-context` (a machine-readable schema for agents) are all generated from these specs, so the docs and the binary cannot drift apart.
- **Orchestration state.** Runs, tasks, dispatches, messages and gates live in a SQLite database, `orchestration.db`, in userData. The coordinator logic in `src/main/runtime/orchestration/coordinator` defaults to 4 concurrent workers, opens a circuit breaker after 3 failed dispatches, and allows nesting up to 4 levels deep.
- **Orchestration wake-up.** Mail is stored in the database, never typed into the agent. To wake a terminal agent, Orca writes a short pointer into its PTY: "You have N orchestration messages. Run `orca orchestration check --run <id>`." Native chat sessions get the message whole as a structured turn, queued until the busy turn ends. The agent then pulls mail with `check`, which is FIFO, one delivery at a time, and acknowledges it. Agent-status hooks (`orca agent hooks on`) tell Orca when an agent is idle or done.
- **Worker spawning.** `worker-start` creates or picks a workspace, launches the agent CLI in a PTY or native chat, and waits for readiness. It then injects a dispatch preamble: Task ID, Dispatch ID, coordinator address, CLI contract, an optional BASE DRIFT section, and the task spec. The worker reports back with `orca orchestration send --type worker_done`. Source: `workers/launch/worker-dispatch-preamble.ts`.
- **Automation scheduling.** A `setInterval` tick runs every 60 s inside the main process, or the headless `orca serve`. It works out which runs are due from 5-field cron, presets, or a restricted RRULE in a timezone, with missed-run grace. Event triggers from Slack, GitHub, Linear, Gmail and Calendar arrive through Orca Cloud connector webhooks. Source: `src/main/automations/automation-service.ts`, `src/shared/automations/scheduling/`.
- **Computer use on macOS** is a signed Swift helper, `native/computer-use-macos` ("Orca Computer Use"), that talks to Node over an authenticated Unix socket. It reads AX trees, posts input to background windows without moving the pointer, and captures screens.
- **Computer use on Windows and Linux.** Windows uses `native/computer-use-windows/runtime.ps1` in `-Serve` mode, one JSON response per line. It drives UI Automation patterns and Win32 P/Invoke via Add-Type. Linux uses `native/computer-use-linux/runtime.py`, an AT-SPI (`gi` Atspi 2.0) adapter that reads a JSON operation file. Wayland screenshots use grim with hyprctl or swaymsg, or the KDE xdg-desktop-portal. A Node sidecar owns the public API and tree diffing.
- **Browser automation.** The built-in per-worktree browser is an Electron guest page driven over CDP through the bundled `agent-browser` (~0.43) package. Typed Orca commands such as `snapshot`, `click` and `fill` wrap it, and `orca exec` is a raw passthrough. Design Mode injects guest content scripts (`src/main/browser/element-grab`) for overlay, element context, React source and screenshot crop.
- **Git hosts.** GitHub goes through the `gh` CLI. Orca classifies REST, GraphQL and search rate limits and runs a circuit breaker per bucket. GitLab goes through `glab` (`GITLAB_TOKEN`/`GLAB_TOKEN`). Bitbucket, Azure DevOps and Gitea use REST with saved credentials or `ORCA_*` env tokens. Linear uses `@linear/sdk`. Jira uses REST, Cloud or Server/DC, with credentials encrypted via the OS keychain.
- **Skills.** Skills are thin "hybrid stub" `SKILL.md` files. The full, version-matched guide lives inside the binary and is served by `orca skills get <topic>`. Orca's own installer and updater rewrites only unmodified copies, recognized by a hash of shipped versions, and plans its writes against a digest.

## Part C: Bots, Plugins, Design system, Engine misc

Source: github.com/stablyai/orca at HEAD b864ea6 (2026-11-24), plus orca.dev/bots and orca.dev/docs/bots{,/connectors,/security,/import,/use-cases}, fetched 2026-11-25. Paths are relative to the repo root.

#### Architecture notes

- **A bot is a folder plus a record.** The record is a Zod `BotSchema` in the profile store. The home folder is `~/.orca/bots/<kebab-folder>/` and holds Orca-generated `AGENTS.md`, `CLAUDE.md` (`@AGENTS.md`) and `bot.json`, the user-owned `SOUL.md` and `MEMORY.md`, plus `memory/` and `skills/<name>/SKILL.md`. The bot runs as an ordinary Orca native-chat session of the user's own agent CLI (23 agents) with its working directory set to the home. Orca injects a preamble (Tools, SOUL.md, MEMORY.md, Rules) before the first message.
- **Orca drives the bot through an `orca` CLI.** The agent controls Orca by shelling out (`orca bot item set`, `orca bot reply`, `orca orchestration worker-start`, `orca automations create`, `orca slack post`). The preamble is mostly a CLI manual plus behavioural rules. When rules change, Orca re-sends them as an "[Orca rules update]" message.
- **The bot delegates code work.** Rules tell the bot never to read code itself. It starts "workers", which are separate agent sessions in a new child git worktree (`--worktree new-child`). Each worker owns its PR until it can merge. Results come back to the bot as mail. Bots, workers and other bots exchange typed mail (`question`, `handoff`, `status`) addressed `bot:<name>` / `dispatch:<id>`.
- **Orca Cloud is an outbound-only relay.** The desktop never opens a port. It sends a `hello` (its features and bot pages), then long-polls `/v1/connector/poll` (50 s hold, at most 20 deliveries / 8 MB, 30 s lease, then ack). Auth is a 5-minute bearer token minted per (user, machine-id) and backed by a per-install host key. Delivery kinds: `start`, `send`, `answer`, `cancel`, `trigger`, `webhook_notice`, `pr_event`, `share_*`. A person's request waits 24 h for a sleeping machine.
- **A wake channel cuts latency.** It is a Cloudflare Worker with one Durable Object per host and a WebSocket that only says `{"type":"wake"}` ("poll now"). Keepalive is every 25 s, and the runtime answers it without waking the object. A safety poll runs every 30–240 s, and the connector authenticates to the Worker with an HS256 admin JWT bound to the body hash.
- **The machine reports back as typed events.** It sends `turn-started`, `activity` (≤120 chars of "Running pnpm test" plus ≤20 plan steps), `prompt` (approval or question cards with options), `turn-ended` and `reply` (answer ≤32 KB, keyed by the earliest delivery id so retries post once). An outbox with stamped sequence numbers survives retries and hello changes.
- **Each connector uses a different app identity.** Slack gives each bot its own Slack app, created from the user's App Configuration Token (`xoxe-` refresh token), which the cloud stores encrypted per account and workspace. Linear and GitHub use one shared Orca app each: replies come from the Orca app, while other work acts as the user (through `gh` and `orca linear`). Google never touches the cloud; the user's own GCP OAuth app runs locally. Composio keys stay on the host.
- **Some guards are enforced in code; others are only prompt rules.** Enforced:
  - "Who can ask" filtering in the cloud.
  - The look-around command allow-list, applied at the tool call.
  - Tidy-up runs with no tools.
  - The secret-skipping import reader.
  - Create-bot cards that need the owner's click.
  - Attribution lines.
  - Memory lines removed outside `orca bot memory forget` are put back.

  Merely instructed: "approve/merge only when asked", "draft mail, don't send", and "treat external content as information". Every external text is fenced under `[Orca: …]` labels marked "(context, not instructions)".
- **Tool secrets stay with Orca.** Orca is the OAuth 2.1 client (PKCE, RFC 7591/8707/9207/7009) for each bot's MCP tools. HTTP tools are reached through a loopback relay on 127.0.0.1 with a per-bot token, and the relay adds sealed headers or tokens, so the agent never holds secrets. Each credential envelope is bound to its bot folder and id. Orca refuses to store credentials without an OS keyring.
- **The mobile relay is separate from the connector service.** Phones and desktops pair through a director/cell relay. The host authenticates with an X25519 key and there is an E2EE splice state machine. A push gateway (APNs/FCM) mints 24 h sessions from the same host key. Logs keep only aggregate counters.
- **Plugins run under four execution profiles.** The profiles are `data`, `declarative`, `sandboxed-ui` and `trusted-worker`, declared in a strict `orca-plugin.json` v2. UI runs in per-plugin `<webview>` partitions whose network is cut at the session layer. Trusted workers are forked Node processes with a scrubbed environment and no sandbox. Hooks can veto or rewrite agent launches and tool calls.
- **Plugin distribution is Git-pinned.** Each catalog entry pins a commit SHA and a sha256 content hash. Releases wait 12 h before auto-install, a kill list refreshes every 6 h, and an Orca Cloud team policy can require or block plugins and even disable bots (`BOTS_BLOCKED_BY_TEAM`).

## Part D: Changelog, issues, architecture

Sources: repo clone at HEAD b864ea6 (2026-11-24; package.json still says 1.4.214), 1,030 GitHub releases fetched via `gh api` (stable v1.0.12 on 2026-03-21 through v1.4.274 on 2026-11-24, plus rc/mobile tags), and GitHub issue search (5,582 open and 7,525 closed issues). Repo stats: 136.8k stars, 8.75k forks, MIT, TypeScript.
Release notes before about v1.4.149 are bare PR lists, so "first seen" for early features comes from PR titles in that release. Release URL pattern: `https://github.com/stablyai/orca/releases/tag/<tag>`.

### Architecture summary

- **Stack:** Electron 43.8.10 with React 19.2, electron-vite 6 / Vite 8, Tailwind 4, Radix/shadcn and zustand 5. Node 24 for the server side, Node 18 for the CLI launcher and WSL guest. About 28k `.ts/.tsx` files under `src/` (`package.json`, `electron.vite.config.ts`, `docs/development.md`).
- **Process fan-out:** `config/build-plugins/main-build-entry-points.ts` defines 37 bundle entries besides `index`. They include:
  - core services: `backend-entry` (a utility process holding core runtime services, linked over a MessagePort; `src/main/backend/`), `daemon-entry` (terminal daemon), `computer-sidecar`, `plugin-host-entry`, `stt-worker`
  - data workers: `session-search-worker-entry`, `usage-scan-worker-entry`, `bots-db-worker-entry`, `journal-sql-worker-entry`, `profile-state-writer-worker-entry`
  - watchers: `parcel-watcher-process-entry`, `main-thread-hang-watchdog-entry`
  - many more single-purpose scanners
- **Main process (`src/main/index.ts`, 299 lines):** installs guards first (fatal-signal and OOM traps, Windows std-handle isolation, WSL gate), then hands off to `src/main/startup/*`. It also handles deep links (`orca://`), single-instance and "orcad sidecar" activation, and a profile-state recovery dialog.
- **Off-main work:** `src/main/utility-worker-host/` runs a heavy-worker host with a heap sampler, crash-loop guard and relay budget. `src/main/worker-threads/` has a lazy worker-thread host, request queue and send ledger. Heavy scans moved there over time: usage scans in v1.4.206, Session History search in v1.4.255, Git work moved to a background worker in v1.4.269.
- **Process spawning:** `src/packages/process-host` (`@orca/process-host`) has no dependencies. It handles bounded output, cancellation, Windows argument quoting and process-tree kill, and is shared by desktop, headless server, CLI, SSH relay and daemon. `native/provider-exec` (C) adds a gated-exec subreaper for agent CLIs.
- **Renderer (`src/renderer/src`):** separate HTML roots for the app (`index.html`), the pop-out dashboard (`popout.html`), Space (`space.html`) and the browser web client (`web-index.html`, `vite.web.config.ts`). Main libraries:
  - xterm.js 6.1-beta with WebGL, ligatures, image, search and unicode11 addons
  - Monaco 0.55 for code; TipTap 3 for rich Markdown
  - shiki, mermaid, KaTeX, pdfjs, @tanstack/react-virtual, i18next
- **Terminal daemon (`src/main/daemon/`):** a long-lived Node process that owns the node-pty sessions.
  - It survives app restarts and app updates. The wire protocol is version-gated, currently v62 (`daemon/protocol/daemon-protocol-version.ts`).
  - Its Unix-socket endpoint uses a strict link/rename ownership protocol (`daemon/AGENTS.md`).
  - Snapshots and scrollback restore come from an in-daemon headless xterm (`daemon/emulation/headless-emulator.ts`, `@xterm/headless` + `addon-serialize`), with storage in `daemon/history/`.
  - New releases sometimes start a "fresh terminal host" while old terminals stay attached to the previous one (v1.4.241, v1.4.243, v1.4.245).
- **orcad / runtime:** `src/main/orcad/` is the Orca runtime daemon, with an instance lock, served profile, relay and native runtime. It boots on plain Node (v1.4.190) and runs headless as `orca serve`. `src/main/runtime/orca-runtime.ts` is the core: workspaces, sessions, terminals, browser, orchestration, bots and automations, all exposed over RPC.
- **RPC/IPC:**
  - `src/main/runtime/rpc/` has 116 method modules over three transports: `unix-socket-transport.ts`, websocket (default port 6768, `rpc/server/runtime-rpc-pairing-types.ts`) and `relay-transport.ts`.
  - Zod-typed contracts live in `src/shared/rpc-contract/` (61 entries).
  - `src/main/jsonl-rpc/` is a JSONL peer used for agent connections (ACP).
  - About 80 Electron IPC domains sit in `src/main/ipc/`, plus the preload bridge `src/preload`.
- **Storage:** profile state moved from JSON to SQLite in v1.4.214. It uses built-in `node:sqlite` `DatabaseSync` (no native SQLite package; `src/main/sqlite/sync-database.ts`), with a writer worker, atomic snapshots, backups and a JSON-vs-SQLite conflict dialog (`src/main/persistence/profile-state/`). `src/main/foreign-sqlite-readers/` reads other agents' session databases, for example OpenCode.
- **SSH:**
  - Two transports in `src/main/ssh/`: the `ssh2` library and the system OpenSSH binary. The system path supports ControlMaster (v1.4.118), Kerberos/GSSAPI (v1.4.142) and multi-factor prompts (v1.4.217). Host-key verification arrived in v1.4.187.
  - Also in `src/main/ssh/`: port forwarding, file transfer and the legacy relay.
  - Since v1.4.224 Orca deploys a managed Orca server, with its own Node runtime, onto SSH hosts. `src/main/managed-server/install/` covers deploy, rollback, GC, Windows launch and a Node mirror.
- **Paired servers and E2EE:** desktop, phone and web pair with `orca serve` hosts.
  - Pairing codes are single-use (v1.4.254). Phone QR codes expire after 10 minutes and links after 60 (v1.4.252).
  - Encryption: tweetnacl `box` (X25519 + XSalsa20-Poly1305) and `secretbox` with HKDF, in `src/shared/remote-runtime/e2ee/node/e2ee-crypto.ts` (mobile e2ee v2 framing).
  - By default `orca serve` accepts only localhost, LAN and Tailscale peers.
- **WSL:** `src/main/wsl/` treats each distro as a host with its own server; WSL connections go through bash and fall back to Node (v1.4.242). `src/wsl-guest/` holds the guest-side agent-hook relay, browser network relay and transport, with a Node 18 minimum.
- **Mobile (`mobile/`):** Expo 58 / React Native 0.88 (`orca-mobile`).
  - Terminals use xterm in a webview; E2EE uses react-native-libsodium; push uses expo-notifications.
  - It connects directly to `ws://<desktop>:6768` on a LAN, or through Orca Relay.
  - Since v1.4.206 the desktop serves an over-the-air mobile web bundle, so UI changes ship without app-store builds (`mobile/modules/orca-mobile-web-shell`).
- **Cloud (`cloud/`):**
  - Phones and desktops never connect to each other directly. Both dial out to the relay, which splices their frames together.
  - `apps/relay`: one image that runs as either the director or a cell, with PostgreSQL in production.
  - `apps/relay-edge`: Cloudflare Workers with Durable Objects `HostRelay`, `SpliceRelay` and `UserHosts`.
  - `apps/relay-ingress`: proxy.
  - `apps/relay-fence-broker`: an IAM-only Terraform mutation lease.
  - `apps/push`: APNs/FCM gateway. The host authenticates with an X25519 challenge and gets a 24-hour session; tokens and notification bodies are never logged.
  - `apps/connector-wake`: Cloudflare Durable Object that holds sockets to wake signed-in Orcas for Slack, Linear and GitHub events. It refuses CN. The connector service itself is closed source.
  - Deployment Terraform lives in a private repo, `stablyai/orca-cloud`.
- **Agent status pipeline:** two channels, described in `src/main/agent-hooks/README.md`.
  - Per-agent managed hooks or plugins POST to a loopback hook server.
  - The OSC 7501 "Program Status Protocol" is parsed from the PTY stream. Hooks take precedence and OSC 7501 fills gaps.
  - On Windows a native Rust hook (`native/windows-agent-hook`) replaces the `.cmd` + curl hook.
- **Native chat:** Claude runs through `@anthropic-ai/claude-agent-sdk` (v1.4.198). Other agents use ACP (`src/main/acp/`, v1.4.223) or transcript readers and watchers (`src/main/native-chat/`, `src/main/ai-vault/`). There are per-agent modules for about 40 agents (claude, codex, opencode/opencode2, pi, omp, grok, hermes, kimi, kiro, cursor, copilot, droid, devin, qoder, goose, and more).
- **Native modules (`native/`):**
  - Swift: computer use on macOS (34 files), keyboard layout, notification-auth status, process footprint
  - Objective-C: macOS menu dead-key fix, ShipIt scheduling
  - Python: Linux computer use (AT-SPI)
  - PowerShell: Windows computer use
  - Rust: Windows agent hook and Windows CLI launcher, a native `orca.exe` because antivirus kept deleting the script version (v1.4.219)
  - C: SQLite journal file lock, provider-exec, Wayland clipboard
  - C++ node-gyp addons: Windows registry, notifications, security
- **Other subsystems:**
  - Speech: on-device sherpa-onnx models (Parakeet, SenseVoice, Zipformer, Nemotron), loaded through transcribe-cpp via koffi FFI in `stt-worker`, with OpenAI-compatible cloud as an option (`src/main/speech/`).
  - Browser automation: the `agent-browser` dependency drives pages over CDP.
  - Computer use: a sidecar process (`src/main/computer/`).
  - Plugins (`src/main/plugins/`): a plugin host worker; isolated processes for panels and editors with network access blocked (v1.4.246); a TS/TSX transpile worker; a catalog. Docs are in `docs/reference/plugin-*.md`.
- **Fleet perf gate (`docs/readme/fleet-perf-gate.md`):** compares old and new builds on a synthetic fleet: 1,900 workspaces (1,800 worktrees + 100 folders), 1,800 chat tabs and 200 terminals.
  - Scenarios: idle 60 s; typing at 10 keys/s; streaming at 20 hook events/s across 10 workspaces; switching; a burst of 25 chats resumed plus 25 new ones.
  - Margins (`fleet-gate-report.mjs`): 25% on message and store-publication rates, 15% on heap (+50 MB main, +100 MB renderer), 50% on long tasks and stalls.
  - Idle ceilings: main→renderer ≤10 msg/s, no-op ≤2, store publications ≤20/s, no-op ≤5.
  - Not in CI: one run takes 25–35 minutes on a 28-core machine.
- **Other perf budgets:**
  - The terminal perf suite was retired. Its last run failed with 104 ms median typing latency against a 75 ms budget at 50 PTYs (`docs/readme/terminal-perf.md`).
  - Default running-terminal limit: half the OS limit, capped at 4,096 (v1.4.245).
  - Memory Saver frees background browser tabs after 4 hours (v1.4.261).
- **Ratchets (`config/*-baseline.txt`, entries may only shrink):** main-blocking-helper 1,577; react-compiler-bailout 712; main-sync-fs 589; focus-setting-read 315; renderer-layout-writer 115; recurring-timer 94; main-blocking-sqlite 91; main-sync-spawn 37; daemon-blocking-call 10. A max-lines ratchet was added in v1.4.128. The scale of these lists shows how much blocking work is still on Electron's main thread.
- **Reliability gates (`config/reliability-gates.jsonc`, 11.7k lines):** 153 gates, all still at "experimental" maturity. Promotion to blocking requires 100 soak runs, 14 days and zero unexplained flakes. Owners are mostly terminal-runtime (37) and terminal-rendering (16).
- **Testing and quality:**
  - Vitest 5 (1,022 `*.test.ts*` files) and Playwright e2e (`@stablyai/playwright-test`).
  - Lint and dead-code tooling: oxlint with custom plugins (anti-slop, react-doctor, design-system, performance-audit, whole-hot-map-selector), ast-grep, knip.
  - `pnpm check:changed` is the local gate. `pnpm test:perf:contracts` runs count-only performance contracts in CI.
  - `AGENTS.md` says tests are the exception: prove a change by running it.

### Trajectory

- **From worktree terminal manager to agent operating system.** March 2026 was worktrees, terminals and PR status. April–May added orchestration, dashboard, automations and mobile. June–October added native Chat UI, a remote/managed server and skills. November added Orca Bots: persistent agents with soul and memory, Slack/Gmail/GitHub/Linear/Discord/Composio connectors, and group rooms spanning computers.
- **Chat UI is replacing the TUI as the primary surface.** It went from experimental (v1.4.111, June) to the Claude Agent SDK and ACP (Sept–Oct) to GA (v1.4.246, Nov 2), and each agent gets its own native chat adapter. Expect terminal-first users to become secondary.
- **Multi-host and distributed by default.** Every feature must work on local, SSH, WSL, paired `orca serve`, VMs and phone (`AGENTS.md` names Remote hosts, Mobile and Folder Workspaces as "first-class citizens"). There is a managed server deployed to SSH hosts, a multi-region cloud relay on Cloudflare plus GCP, and bots that run across computers.
- **Fighting Electron's ceiling.** Since October most headline releases have been about performance and memory (v1.4.242 "lighter on memory", v1.4.245 "A faster Orca", v1.4.259/261/262 "major performance improvements"), with GPU and Linux memory leaks along the way. The fleet gate at 1,900 workspaces, 1,500+ main-thread-blocking ratchet entries and the maintainer's "Performance 100x'd" thread all show this is a structural fight.
- **Platform play.** Plugin system and community catalog (TS/TSX panels, custom editors, themes), skill distribution to 30+ agent CLIs, a self-describing `orca` CLI for agents, artifacts sharing and an optional Orca account point toward an ecosystem and possibly a hosted business (closed connector service, push gateway, relay).
- **Breadth over depth.** They support 35–40 agent CLIs, each with usage meters, account switching and session history, plus a Chrome-like browser (extensions, passwords, DevTools) and on-device dictation. The core code editor still lacks LSP, multi-window and multi-root diff, which are the top-voted gaps.
- **Velocity is extreme.** 402 stable releases in 8 months (v1.0.12 to v1.4.274, about 1.6 a day) and PR numbers near #48,800. Hourly, nightly and adhoc channels and "fresh terminal host" upgrade notes show heavy churn. Orbit can win on stability and a coherent native UX rather than on feature count.
